## Operator workflow

Run migration `0023` before starting this release. The existing `ADMIN_API_TOKEN`
must contain at least 32 characters. No additional service, credential, frontend
build or consumer account is required.

For local development, start the normal API and open
`http://127.0.0.1:8000/admin`. After deployment, use the existing private SSH alias:

```sh
ssh -N -L 127.0.0.1:8035:127.0.0.1:8000 travel-scam-prod
```

Open `http://127.0.0.1:8035/admin` on that same computer. This forwards to the API's
existing host-loopback binding through SSH over Tailscale. Do not publish this port
or add `/admin` or `/v1/admin` to Caddy/Funnel. Public REST/admin/media remain blocked.

Enter the existing admin token in the password field. It is sent only in the
Authorization header and kept in memory; it is never put in URLs, cookies,
localStorage or sessionStorage. Lock/clear and page teardown clear private records,
draft fields, token and image object URLs. A self-contained login shell is available
without authentication, but it contains no records. All admin data and command
routes require the token, fail closed when it is unconfigured, and use `no-store`
even for errors. The shell uses exact script/style CSP hashes, same-origin reads
and no frames, external assets or third-party scripts.

Choose a queue, optionally filter by status, and click **Refresh list**. Name/title
search applies to locations and hypotheses. Report status filters use moderation
status; jobs/documents use processing status. Resolution review defaults to pending,
unapplied decisions; `all` includes history. Pagination bounds API reads to 50 records
(20 evidence records) and the UI uses 20. Emerging-review pagination retains its
existing 1,000-offset bound; the other admin queues use 10,000.

Inspect the record and its evidence before choosing an action. Merge/move require
loading the target hypothesis; split/move require selecting current evidence.
Every action requires a reason, a separate review preview and an explicit checkbox
before commit. The UI binds its request to the inspected timestamps or moderation
revision. On a definite conflict, reread and decide again. On an uncertain network
outcome, keep the view open, re-confirm and retry the exact action; the same frozen
payload and idempotency key recover the receipt. Locking/closing discards this
in-memory retry context, so reconcile uncertainty first when possible.

## Available operations and limits

| Area | Behavior |
| --- | --- |
| Hypotheses | Inspect candidates, edit title/description/category, review status, merge or split; inspect current and archived evidence. |
| Evidence | Move up to 100 selected attachments between current hypotheses at the same location. Original attachments are archived and point to replacements; claims and source geography are retained. Split also allows 100; merge retains its existing 1,000-evidence bound. |
| Resolution review | Inspect claim, candidate descriptions, review reasons and comparator rationale; apply an unchanged recorded resolution. Existing claim, geography, candidate and embedding snapshot checks remain mandatory. An invalid/outdated resolution must be regenerated by the existing processing workflow. |
| Reports | Inspect private text and authenticated normalized attachments; mark needs-review, reject, or accept through the existing moderation safeguards. Sensitive/unresolved text cannot be released simply by accepting it. Reopen a rejected report before attempting acceptance. |
| Emerging candidates | Inspect the existing queue and acknowledge/dismiss a pending revision. This does not verify, publish, rescore or change confidence. |
| Jobs | Inspect failed and research jobs, resource usage and references without exposing lease tokens, arbitrary payloads or provider completions. Reissue only failed ingest/process/report jobs as new bounded jobs. |
| Documents | Inspect bounded normalized text and request normalization of the stored raw external document. This is not fresh semantic extraction or a new search. Private report documents require the guarded report retry instead. |
| Locations | Inspect current research/root state, partial coverage, stop reasons, continuation usage/caps and retry time. Set/reset a location scheduler adjustment from −100 to +100. |
| Audit | Read timestamp, operation, subject, shared-token actor and reason across new admin actions and existing lifecycle, report-moderation and emerging-review decision history. |

An explicit failed-report retry may spend Sarvam calls within existing per-job
limits. Held/rejected/needs-review reports cannot use it. Retry creates a new job,
retains the failed job's attempts/history, advances the report revision, and cannot
reset an active lease or a location/hypothesis research job. Equivalent active work
blocks another reissue. Committed jobs survive Redis dispatch failure and remain
available to the existing worker's durable outbox dispatcher. The command itself
does not fetch sources, call an LLM, reset research cursors or increase root budgets.

Priority adjustments affect only already eligible **location** scheduler candidates.
They do not enable the scheduler, create demand, revive dormant locations, skip retry
cooldowns/freshness, cancel active research, reserve extra budget or prioritize
hypothesis jobs. The normal cycle/daily admission checks still apply. A positive
adjustment orders eligible candidates earlier before the bounded candidate limit,
then adds to their calculated priority; zero restores normal ranking.

Graph/status changes preserve the existing derived-score invalidation rules; text
edits also invalidate embeddings. This dashboard does not synchronously recompute
scores, refresh vectors, or provide a general semantic-extraction reset. Use existing
maintenance/research workflows for those tasks. A status of `active` is a curation
decision, not a verified incident. It cannot bypass sensitive/held claims, geography,
source grounding, English-language, moderation or attachment-publication safeguards.
Ordinary low-confidence candidates remain eligible under the existing public rules.

## Transaction and audit contract

`POST /v1/admin/commands` accepts a discriminated `operation`, `subject_id`, reason,
strict `confirmed=true` and its operation-specific fields. Send an `Idempotency-Key`
of 16–128 permitted characters. The private `admin_actions` ledger hashes keys and
canonical input; it does not store bearer tokens or raw keys. Exact replay returns
the original action/result before checking now-stale input versions. Changed input
with an existing key conflicts. Mutation and audit commit together; concurrent
exact requests produce one action. Each new decision gets a new key.

Hypothesis/source/target rows are locked in UUID order. Evidence moves reuse the
lifecycle attachment/archive and derived-cache invalidation machinery. Non-research
job reissues use a work-specific transaction lock and active-equivalent check.
The shared bearer token is recorded as `admin-token`: this provides an operational
history, not named-user attribution or a tamper-proof audit service. Reasons are
private but operators should still avoid entering unnecessary identifying data.

Existing report-moderation and emerging-review endpoints remain available; the
dashboard uses the new command ledger around their domain helpers so lost responses
can be replayed without another decision. Audit may therefore include both an admin
receipt and its domain event; these are two records of one action, not independent
reviews.

Migration `0023` adds `admin_actions`, a zero-default bounded location priority and
the lifecycle `move` operation. Prefer rolling back the application image while
retaining this additive schema. A database downgrade deletes the new admin ledger
and priority overrides; archive that private history first if a downgrade is truly
needed. Downgrade deliberately retains the widened lifecycle constraint so existing
move history is never discarded to force an older enum. Re-upgrade is supported.
